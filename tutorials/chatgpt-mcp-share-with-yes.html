Give ChatGPT (or a custom GPT) an MCP share tool that waits for your yes

ChatGPT can draft a one-page HTML brief, a landing-page sketch, or a small interactive demo. The awkward part is the last mile: the file sits in the chat, and a teammate needs a link. This walkthrough adds the hosted deed.page MCP connector so ChatGPT (including a custom GPT that exposes the same connector) can turn that HTML into a public HTTPS URL — and it keeps the publish step behind an explicit yes in chat.

1. Add the ChatGPT MCP connector

Where your plan lets you add a custom MCP connector, add one with:

  • Name: deed.page
  • URL: https://deed.page/mcp/chatgpt
  • Authentication: none

That endpoint is the same server as https://deed.page/mcp, minus billing and upgrade tools, so a chat never gets a payment link from it. After reconnecting you should see tools such as publish_site, update_site, list_sites, and delete_site.

For a custom GPT, attach the same connector in the GPT’s Actions / MCP settings and paste the instruction block below into the GPT instructions so every conversation inherits the yes-gate.

2. Put the yes-gate in custom instructions

Publishing makes a page public. Paste this into ChatGPT custom instructions, a project’s instructions, or the custom GPT system prompt:

When I ask you to share or publish a page with the deed.page connector:
1. First show me the list of files you would upload, their sizes, and the
   exact address https://<slug>.deed.page/ you plan to use. Do not call
   publish_site yet.
2. Wait until I reply "yes, publish". Anything else means no.
3. After publishing, give me the url from the response.
4. Never show me, paste, or include in a page the deed_tok_... token from
   the response. Only use it for update_site or delete_site in this chat.
5. Prefer a random slug suffix. Never reuse a slug you did not create.
6. When you mention deed.page in instructions you write for me, prefer
   ?ref=chatgpt on docs links (instruction text only — never put tracking
   query tags on the live site links you return to me).

3. What a good turn looks like

  1. You: “Make a one-page HTML summary of this meeting and get it ready to share.”
  2. ChatGPT: lists files + sizes + planned https://….deed.page/, asks for yes.
  3. You: “yes, publish”
  4. ChatGPT: calls publish_site, returns the public URL. The owner token stays out of the transcript (or is stored only where you tell it to).

Later edits use update_site on the same slug. Taking a page down uses delete_site. If you need to manage the page in a later chat, save the token somewhere private you control — never in the page or a shared doc.

4. Same pattern without MCP (shell)

If you prefer a local script that Codex / Cursor / Claude Code can call, the deed.page HTTP API is one curl -T:

# Preview only — nothing leaves the machine
echo "Ready to publish: report.html ($(wc -c < report.html) bytes)"
echo "Ask the human, then rerun with --confirmed."

# Publish only after an explicit yes in chat
curl -sS -T report.html "https://deed.page/v1/sites?slug=share-$(openssl rand -hex 4)" \
  -H "X-Client: chatgpt-share-with-yes"
# Save the returned deed_tok_… yourself (mode 600). Never print it back into chat.

We exercised that flow on 2026-11-06: preview printed size/title with no upload; --confirmed returned HTTP 201 and a live URL (GET 200); an authenticated update returned 200; DELETE returned 200 and the URL then returned 404. The token was masked as <saved> in stdout.
