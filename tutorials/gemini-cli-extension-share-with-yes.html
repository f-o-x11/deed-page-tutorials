Gemini CLI extension: share HTML only after the user says yes

Gemini CLI can already write a status page, an experiment log or a small interactive chart as a single HTML file. The awkward step is getting that file onto the public web without turning the model into an unattended publisher. This walkthrough wires a tiny shell helper into a Gemini CLI extension so the model can propose a share, show you the preview, and only upload after you type an explicit yes in the chat.

What a Gemini CLI extension is here

A Gemini CLI extension is a public repo with a gemini-extension.json at the root (and usually the GitHub topic gemini-cli-extension). The gallery at geminicli.com/extensions crawls those files; there is no separate submission form. Your extension can declare MCP servers, ship skill text the CLI reads, and include helper scripts the model is allowed to run. The deed.page skill repo already ships a gemini-extension.json that points at the hosted MCP; this tutorial shows the complementary pattern of a local share-html.sh for one-file HTML when you want the upload path under your own eyes.

Two calls, never a silent upload

Do not put a "Publish? [y/N]" prompt inside the script. The Gemini CLI shell is not a terminal you are staring at, and the model can answer that prompt for you. Split the flow into two invocations instead:

1. share-html.sh report.html prints path, byte size and <title>, reminds the model that publishing makes the file public, and exits without touching the network. 2. share-html.sh report.html --confirmed uploads with curl -T and prints the public URL.

Put the second call behind a hard rule in the extension skill text: never pass --confirmed unattended, and never invent a yes from a prior turn. Only the human's current reply counts.

The script

Ship it as bin/share-html.sh inside the extension (or under ~/.gemini/extensions/deed-page/bin/ after install) and mark it executable. It publishes through deed.page: one HTML file, one curl -T, no account. The first successful upload returns an owner token; the script writes it to ~/.config/deed-page/token with mode 600 and rewrites the JSON so the token never appears in the Gemini transcript.

#!/usr/bin/env bash
# share-html.sh FILE [--confirmed]
# Preview (no --confirmed): print path/size/title and exit. No upload.
# --confirmed: upload via curl -T to https://deed.page/v1/sites
# Gemini CLI / extension skills must NEVER pass --confirmed unattended.
set -euo pipefail
FILE=${1:?usage: share-html.sh FILE [--confirmed]}
[ -f "$FILE" ] || { echo "No such file: $FILE"; exit 1; }
TITLE=$(grep -o -i -m1 '<title>[^<]*' "$FILE" | sed 's/<title>//I' || true)
if [ "${2:-}" != "--confirmed" ]; then
  echo "Ready to publish: $FILE ($(wc -c < "$FILE") bytes, title: ${TITLE:-none})"
  echo "Publishing makes this public on the internet. Ask the user, then rerun with --confirmed."
  exit 0
fi
CONF=~/.config/deed-page; KEY=$(printf '%s' "$(realpath "$FILE")" | sha1sum | cut -c1-10)
SLUG=$(cat "$CONF/slug-$KEY" 2>/dev/null || echo "share-$(openssl rand -hex 4)")
TOK=${DEEDPAGE_TOKEN:-$(cat "$CONF/token" 2>/dev/null || true)}
set --; [ -n "$TOK" ] && set -- -H "Authorization: Bearer $TOK"
RESP=$(curl -sS -T "$FILE" "https://deed.page/v1/sites?slug=$SLUG" "$@" -H "X-Client: gemini-cli-share-html")
NEW=$(printf '%s' "$RESP" | sed -n 's/.*"token": *"\(deed_tok_[^"]*\)".*/\1/p')
(umask 077; mkdir -p "$CONF"; printf '%s' "$SLUG" > "$CONF/slug-$KEY"
 [ -n "$NEW" ] && printf '%s' "$NEW" > "$CONF/token") || true
printf '%s' "$RESP" | sed 's/"token": *"[^"]*"/"token":"<saved>"/' \
  | python3 -c 'import json,sys; d=json.load(sys.stdin); print(d.get("url") or d)'

Skill text the extension should teach Gemini CLI

Keep this next to gemini-extension.json (for example in skills/deed-page/SKILL.md or a short GEMINI.md the extension loads). The important lines are the ones that forbid an unattended --confirmed and forbid reading the token file into the model context.

## Sharing an HTML file from Gemini CLI
- When the user asks to share, host or publish an HTML file, run
  `bin/share-html.sh <file>` first and show them the preview summary.
- Ask "Publish this to a public URL?" and stop. Only after they reply yes
  in this conversation, run `bin/share-html.sh <file> --confirmed`.
- Never pass --confirmed on your own. Never open, cat or print anything
  under ~/.config/deed-page/. Never paste the owner token into chat.
- Re-sharing the same file: preview again, wait for yes, then --confirmed.
  The slug stays stable so the URL does not change.

Minimal gemini-extension.json

Enough for the gallery crawler and for Gemini CLI to discover the MCP. Pair it with the skill text above and the bin/share-html.sh helper.

{
  "name": "deed-page",
  "version": "1.8.0",
  "description": "Publish a single HTML file to a public deed.page URL only after the user confirms. Preview first; never upload unattended.",
  "mcpServers": {
    "deed-page": { "httpUrl": "https://deed.page/mcp" }
  }
}

What happened when I ran the script

I exercised the same two-call pattern Gemini CLI would use, against a 120-byte gemini-demo.html titled "Gemini CLI share demo". The preview call printed path, size and title and left no network traffic and no files under ~/.config/deed-page/ for that path. The --confirmed call returned a live https://share-xxxxxxxx.deed.page/ URL (HTTP 200). Editing the heading and running --confirmed again updated the same slug. Stdout showed <saved> instead of the token, and the token file was mode 600. A DELETE with that token returned 200 and the URL then returned 404.

Removing a page

curl -X DELETE "https://deed.page/v1/sites/<slug>" \
  -H "Authorization: Bearer $(cat ~/.config/deed-page/token)"

The slug is the hostname label before .deed.page. Run DELETE yourself rather than asking the model to, because it must read the token.
